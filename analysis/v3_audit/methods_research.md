# Methods research for the next MSCapital experiment

Sources verified 10 September 2026; compute status updated 11 September 2026. Scope: the supplied competition, existing v1/v2 artifacts, and one local overnight budget on an RTX 3060 Ti with 8 GB VRAM, 32 GB RAM and 8 CPU cores / 16 threads. Recommendations below are hypotheses to test, not claims of private-leaderboard improvement.

The strongest next experiment is a controlled comparison using the information already extracted: give TabM the same 754 engineered inputs as LightGBM, and compare a small temporal network on the existing ordered bins against that full-feature TabM. Separately test the tree preprocessing and evaluate the complete blend at a 38-month deployment age. A larger sequence model should earn its place through complementary predictions and temporal stability. The available evidence does not establish a universally best architecture for this hidden return target.

## What the competition actually establishes

I read the rendered Kaggle pages in the in-app browser because text-only web retrieval returned empty page shells. The [official overview](https://www.kaggle.com/competitions/ms-capital-real-financial-market-forecasting/overview) gives the evaluation as `cos(prediction, target)`: standard uncentered vector cosine, consistent with the implementation in `analysis/modeling.py`. The organizer does not publish a longer metric implementation on that overview. The attached screenshot shows the latest score as **0.133**, following **0.124**; 1.333 is a transcription error, not a score on this metric.

The [official data description](https://www.kaggle.com/competitions/ms-capital-real-financial-market-forecasting/data) establishes labeled months 0-70 and combined test months 71-108. Calendar dates and target-generation details are withheld. Market data contains approximately 600 seconds of time bars with two book levels; raw orders and trades cover about 60 seconds. Order side 0 means buy and 1 means sell; action 0 means new and 1 means cancellation. Trade side denotes aggressive buying/selling. The data page explicitly prohibits external data and models. The [generic rules](https://www.kaggle.com/competitions/ms-capital-real-financial-market-forecasting/rules) allow external material only unless the host prohibits it, so they do not override that restriction. Use competition-only training data and no imported fitted model weights. A published architecture or optimizer recipe trained here from random initialization is a different object from an externally trained model; the pages do not provide an architecture-by-architecture ruling. None of the proposals needs a pretrained foundation model.

The [leaderboard](https://www.kaggle.com/competitions/ms-capital-real-financial-market-forecasting/leaderboard) confirms approximately 49% public and the other 51% for the final results. It does **not** disclose that public rows are the earlier months or private rows the later months. Do not reconstruct either partition from sample IDs. The combined 38-month future period is established; partition chronology is unknown.

## The information comparison is currently unequal

V2 LightGBM receives the 474 base inputs plus 280 path features. The promoted TabM runner materializes only the base feature set. The path features are not merely aggregate summaries without time order: `analysis/v2/sequence_features.py` stores ten consecutive six-second bins, with 11 market, 11 order and 6 trade channels per bin. LightGBM sees these as 280 named columns. Time has been coarsened and flattened, but not erased. Bin zero is the newest; temporal code must explicitly reverse to oldest-to-newest if that is its convention.

This creates two separate research questions. First, does a shared temporal encoder learn more useful interactions than a tabular model on **exactly the same cached information**? Test full-feature TabM against a small convolutional encoder of the ten-by-28 array plus the base-feature branch, using the same folds, target, preprocessing contract and epoch-selection discipline. A temporal model beating base-only TabM would not isolate the architectural contribution. Second, does richer data from the original 600/60-second histories improve either model? That requires new extraction and a later controlled comparison.

The [validation audit](<validation_audit.md>) finds that capacity changes contributed more to the tree improvement than the additional path inputs. It also identifies reused evaluation labels. The research does not erase those limitations: all already-examined months remain retrospective development evidence, even with a new runner or a newly frozen recipe.

LightGBM also deserves its own preprocessing. Its [official documentation](https://lightgbm.readthedocs.io/en/stable/Advanced-Topics.html) supports NaN handling by default. The current shared `RobustPreprocessor` imputes, adds missing flags and hard-clips scaled values at 8. Clipping merges distinct tail observations; imputation removes the original missing route, although the flags retain missingness information. This is a plausible information-loss mechanism, not a demonstrated scoring bug. Compare unchanged tree hyperparameters on (a) the existing preprocessing, (b) retained tail order without hard clipping, and, if affordable, (c) native NaNs. Keep invalid prices/denominators missing and real zero flows zero. These comparisons determine which change helps; a combined raw/native run alone cannot attribute the gain to one cause. Neural scaling remains a separate requirement.

## What to optimize for cosine

For a fixed deployment distribution, finite second moments and many observations, write the population objective as

`C(p) = E[p(X)Y] / sqrt(E[p(X)^2] E[Y^2])`.

Since `E[p(X)Y] = E[p(X) E[Y|X]]`, Cauchy-Schwarz gives the optimal prediction direction `p(X) ∝ E[Y|X]`, with a positive proportionality constant. This is a population argument, not an exact guarantee for a small dependent test set or a restricted model class. It explains why ordinary squared-error regression is a legitimate starting point despite the cosine scoring rule.

Three consequences are useful here:

1. A global positive rescale does not change cosine, but changing relative amplitudes across samples does. Ranking, centering, per-month normalization and predicting only signs can remove valuable amplitude information. Ordinary correlation or rank IC cannot replace the official pooled score.
2. Heteroskedasticity does not make inverse-variance position sizing optimal for this metric. Predicting `mean / variance` is a portfolio decision with a different objective. A model of uncertainty can help estimate or regularize the conditional mean, but uncertainty prediction alone is not directional alpha.
3. If training uses `z = Y / s(X)`, where `s` is a positive scale known at prediction time, restore `p = s(X) f(X)`. Keeping `f` unscaled changes the target. Weighting the normalized squared loss by `s(X)^2` exactly recovers original-scale MSE; unweighted normalized loss is a different finite-model emphasis, even though an unrestricted conditional-mean predictor can recover the same mean after rescaling. Scale floors, bounds and fits must be chosen within the training chronology.

A small later experiment can learn a **shrunk amplitude correction** from earlier out-of-fold predictions, using a few feature-defined spread/activity/volatility groups. For baseline `p` in group `g`, the population least-squares multiplier is `E[pY|g] / E[p^2|g]`; use heavy shrinkage and validate on later groups of months. This tests signal reliability, rather than simply amplifying volatile observations. Never fit the multiplier on the evaluation labels to which it is applied. Do not use weights depending on the same row's realized `|Y|` without acknowledging that they change the conditional target. The existing small signed-power improvement is useful evidence, but does not justify a wide new calibration search or a noisy minibatch-cosine loss.

## Compact sequence design if the cached-bin test is useful

The domain-informed extension is two temporal streams: market state/changes over 600 seconds, and order/trade flow over the last 60 seconds. Start with about 100 coarse market bins and 30-60 short flow bins, not thousands of padded raw events. Use relative mid-price movements, spreads, microprice displacement, two-level imbalance, depth-normalized flow, signed new/cancel quantities, trade direction, activity counts, elapsed time and observation-validity indicators. Compute differences from observations within the same sample; sample IDs do not establish a continuous instrument history.

Signed order pressure should distinguish buy additions / sell cancellations from sell additions / buy cancellations. Keep those channels available separately because equal signed totals can arise from different mechanisms. Include age and validity for matched book observations, and actual event counts for empty or truncated windows. Do not silently fill unavailable price/depth references with a meaningful zero or create synthetic recent observations by backfilling. Normalization constants must be available in the sample at prediction time or fitted on earlier training data. Reference levels can be shared across a fully historical sample without label leakage; claims of online causality at every internal bin require stricter prefix-only normalization.

A width-32 or width-64 residual TCN, a small pooled/terminal representation and a modest static-feature branch should be enough to test the hypothesis. A 32-64-unit GRU is one subsequent alternative if the TCN produces complementary signal. Start from random weights, MSE and inner chronological epoch selection. Choose at most one additional seed for a promising architecture before broadening the model family. These dimensions are proposed starting points, not benchmarked optima.

## Fit the work to one overnight budget

The historical local TabM benchmark took roughly 18-31 minutes per development fold on CPU and reports about 6.1 GiB process memory. Those measurements include its selection/refit workflow and are useful feasibility evidence; they are not RTX timings. Its tested Torch build had no CUDA support. The new local runtime is Torch 2.11.0+cu128. The coordinator verified CUDA arithmetic, and an independent 11 September process/GPU check found the new TabM run alive with the RTX 3060 Ti at 71% utilization and 2,355 MiB of 8,192 MiB used. That establishes usable GPU execution; completed-fold timings are still needed to measure the speedup.

At 1,257,637 rows, 754 float32 features occupy about 3.79 GB before missing flags, transformed copies, training subsets, tensors and LightGBM buffers. Process memory, disk throughput and cache duplication can matter more than parameter count. For illustration, 100×12 market values plus 60×12 flow values stored as float16 would occupy about 4.83 GB for training alone, excluding masks and metadata. Stream or memory-map such caches; do not plan to put all data and optimizer activations into an 8 GB GPU. Float16 is a storage choice only after feature ranges and quantization error are checked; raw small price differences need adequate precision.

An eight-hour allocation is a planning ceiling, conditional on measured runtime:

| Allocation | Experiment or check | Decision it resolves |
|---|---|---|
| First 30-45 minutes | GPU/runtime smoke test, aligned cached-input check and timing pilot | Whether longer runs fit the actual available machine; no parallel GPU trainers |
| About 2 hours | Full-feature TabM and one small cached-bin temporal challenger, with fixed budgets and inner selection | Additional input information versus temporal architecture; preserve both failures and successes |
| About 1-1.5 hours | Bounded LightGBM tail/missingness ablation on the same rows | Whether neural-oriented preprocessing suppresses useful tree information |
| About 1-2 hours | Complete existing blend frozen at months 0-20, forecasting 21-58 | Performance through 38 months without refreshing weights; this origin has less training history than final deployment |
| Remaining time | Confirm the useful candidate on later historical folds; one extra seed if affordable; inference/resource checks | Whether the gain survives chronology and is useful in a fixed blend |

The queue must stop or shorten lower-priority work when measured timings exceed the budget. The allocations do not guarantee every experiment fits. Larger raw-history extraction, full RealMLP training and extra architectures are follow-on work, not simultaneous overnight commitments. The subsequently frozen `artifacts/v3/bounded_experiments/protocol.json` is the authority for the actual run: base TabM, full-feature TabM, a cached-bin temporal model, native-missing LightGBM and the fixed age-38 origin. This memo's broader ablation schedule is research guidance, not evidence that all proposed runs were launched or completed.

Promotion should depend on paired pooled cosine, month-level gains, removal of dominant target-energy months, and prediction complementarity under a small predeclared blend rule. The 38-month test must include the neural component, component normalization and final amplitude transformation. Age slices from one origin are not independent replications; overlapping origins are not millions of new independent observations. Months already used for research cannot become a new untouched holdout. A promising retrospective result supports trying a new submission; it cannot certify a frontier private-test score.

The highest-value unavailable metadata remains instrument identity, actual sample timestamps and the target's support interval. If organizers provide those, they enable principled overlap purging and deduplication. Without them, a coarse month-gap sensitivity analysis is useful but cannot prove all target-window overlap is absent. New external market histories or pretrained financial models would not solve this competition's permitted-data problem.
